## 一、我们做了什么

本次课程包含两条并行的线：一条是**大创项目线**，一条是**Agent 工程线**。两条线的共同任务是：在真实的立项过程中，让 Agent 暴露问题，再把问题修好。

### 1.1 大创项目线

选题为「社区老年助餐的需求预测与营养约束备餐辅助系统」，方向属社会治理和公共服务。

项目要解决的问题是：**社区助餐点经营者无法预知次日有多少老人来吃饭，只能凭经验备餐，导致备餐不足与食材浪费同时存在。**

我们完成的工作：

| 阶段 | 产物 |
|------|------|
| 选题 | 3 个候选选题 + 决策矩阵（7 指标加权评分） |
| 论证 | 证据与假设台账（24 条结论，全部标注 F/I/H/S） |
| 立项 | 一页项目立项说明书、用户与场景分析、关键假设与验证计划 |
| 方案 | 核心机制设计、4 种替代方案比较、单位经济测算、三情景财务 |
| 风险 | 7 类风险识别、合规与伦理边界、能力缺口声明 |

**证据基础**：取得 A 级权威来源 2 项（民政部《2023年民政事业发展统计公报》、民政部等 11 部门《积极发展老年助餐服务行动方案》民发〔2023〕58号），B 级来源 4 项（人民日报《健康时报》、青岛日报、华商报、重庆日报）。

## 二、最重要的三件事

### 2.1 我们差点把「编造」写进了系统里

回顾整个过程，最危险的发现不是某个功能不好用，而是**V1 的证据分类器会把没有任何来源的陈述判为「事实 F」，并标记为「可以直接采用」**。

测试时输入「学校支持建立教材交易平台」——这句话没有任何来源——系统给出的标签是「事实：已有可定位来源或明确材料支持」，可用性为「是」。

这意味着：如果学生直接使用这个输出，就会把一个凭空断言写进立项材料，并且带着系统背书的「事实」标签。

**这个问题不能靠「改改提示词」解决，因为它出在兜底逻辑上。** 我们重建了分类器，把默认值从「F」改成「推断/待核验」，并要求 F 必须有明确的来源标记才能成立。同时对「无来源」「没有调研」这类否定式表述做了专门处理——原来的关键词匹配会因为「无来源」字面包含「来源」而把它当作存在证据。

### 2.2 我们发现了自己的「好评倾向」

同一批修复前，F3 评审流程给一个明确写着「无来源」「创新点是使用AI」「盈利依靠广告」的项目打了 **87 分**，而且证据缺口列表是**空的**。

修复后，同一个输入得 **23.8 分**，质量等级 1（严重缺陷），证据缺口 15 条，并主动提示了两条诚信风险。

这个反差让我们意识到：一个打分系统如果只做「关键词有没有出现」的匹配，它实际上是在**奖励会堆词的人**，而不是奖励有证据的人。我们因此给评分加了证据门槛——全篇没有可定位来源时，任何维度不得超过满分的 40%；创新点如果只落在技术采用上，创新维度不得超过 30%。

### 2.3 我们学会了把「不好看」的东西留下来

课程手册反复强调：不得删除失败样本、不得把人工成果记成 Agent 能力、降级必须如实标注。

我们在实现中把这条落到了具体的地方：

- LLM 服务不可用（API 余额不足）时，系统会**如实标记为 `degraded` 状态**，而不是继续记录成功；用户在界面上也会看到「当前运行于本地确定性模式」的提示。
- 我们**没有删除**那 4 个最初未通过的测试项，而是修好它们并保留了修改记录。
- 我们的证据台账里保留了**对自己不利的条目**——例如「核心问题判断目前只有 B 级证据支撑」，以及「微信群接龙预订已经解决了部分问题，这是我们必须承认的现有做法」。

## 三、遇到的困难与怎么解决的

| 困难 | 表现 | 解决方式 |
|------|------|----------|
| LLM 服务不可用 | DeepSeek API 返回 402（余额不足），所有大模型调用失败 | 把架构改为「确定性引擎为主、LLM 为可选增强」。F1/F3 完全不依赖大模型，F2 降级后仍输出完整结构并如实标注 |
| 自我测评的偏差 | 自己设计的测试用例，容易只覆盖自己想得到的问题 | 明确在报告中写出这一局限，不把「自测全通过」表述为「系统没问题」 |
| 评分标准的主观性 | 最初用关键词命中就给分，结果明显失真 | 改为「必备证据命中比例 + 证据门槛封顶」，并把评分口径写进输出，使结论可复核 |
| 证据收集的边界 | 权威来源只支撑人口规模与政策要求，支撑不了「浪费严重」这一具体判断 | 如实写出这个缺口，把比例类数字全部标注为「媒体报道转述」，不做外推 |

## 四、我们做得不够的地方（诚实清单）

1. **自测存在自证偏差**。全部测试用例由我们自己设计，因此只能覆盖我们已经想到的问题；我们没想到的失败模式，测试是抓不到的。「77/77 通过」只说明已定义的问题都修好了，不说明系统没有别的毛病。
2. **LLM 主路径未经验证**。由于 API 余额问题，F2 的大模型路径始终没有在有效额度下运行过。我们验证的是降级路径。
3. **F1/F3 没有会话归属**。这两个流程的对话记录不进入服务端会话，教师端看不到学生在这两个流程中的使用情况。已列入延期项。
4. **大创项目的核心问题判断证据等级偏低**。A 级来源只支撑人口规模和政策方向，不支撑「备餐浪费严重」这一具体结论，后者目前只有 B 级支撑。
5. **营养约束部分只有概念设计**。团队缺少营养学专业能力，在营养师顾问到位前，这部分不产生任何面向真实老人的饮食建议。
6. **商业模式偏弱**。单位经济测算显示单点年收入约 4320 元，客单价很低，第一年在悲观情景下明确亏损。

## 五、收获

- **学会了区分「看起来对」和「有证据」**。一个系统输出流畅、结构完整、看起来专业，和它说的东西有依据，是完全不同的两件事。
- **理解了降级设计的重要性**。系统在依赖项失效时的行为，比它在一切正常时的表现更能说明它是否可靠。
- **认识到诚实记录的成本与价值**。把失败、降级、延期、能力缺口如实写出来，短期内让材料「不好看」，但它让整个论证变得可信——这正是这门课真正在训练的东西。
