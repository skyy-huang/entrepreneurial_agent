## 二、我在这次课程里最重要的收获

这次课程让我真正理解了「降级」这两个字的分量。

我们的 Agent 依赖外部大模型服务。测试到一半的时候，API 返回 402（余额不足），所有模型调用全部失败。

旧版本的处理方式是：调用失败 → 用本地规则兜底 → **然后记录一条 `status: "success"`**。

从功能上看，用户还是拿到了回复，好像没什么问题。但从审计角度看，这是**日志失真**——它把一个「依赖项失效、系统降级运行」的事实，伪装成了一次正常成功。如果有人后来翻日志想确认「这次到底有没有真正调用大模型」，他会得到错误答案。

我把它改成：降级时标记 `degraded: true`，记录降级原因，最终状态写 `degraded` 而不是 `success`，并且在返回给用户的回复开头就明确写出「当前运行于本地确定性模式」。

这件事让我意识到，**系统在依赖失效时的行为，比它在一切正常时的表现更能说明它是否可靠**。一个只会「成功」的系统，和一个会如实报告自己状态不好的系统，后者才是可以信任的。

另一件事是测试。我一开始写的测试全是通过的，我挺得意。后来发现是因为我的断言写得太宽松——比如「响应状态码是 200」这种断言，几乎不可能失败。真正开始出问题，是我写了 U2 那条「无来源材料中不出现事实 F 判定」之后，它立刻失败了。**好的测试不是证明自己对，而是能抓住自己错。**

## 三、我遇到的最大困难与解决过程

**最难的 bug 是「无来源」被判定为「有来源」。**

现象是：一个明确写着「无来源」的项目，评审结果里证据缺口是**空的**。我一开始完全想不通——我明明写了证据检测逻辑。

定位过程：我把检测函数单独拿出来跑，输入「团队没有调研数据」，结果返回「存在证据」。原因是我用的关键词匹配里有一条「调研」，而这句话里确实有「调研」两个字——只不过前面跟着否定词。

**根因是：关键词匹配对否定式完全失效。**

修复时我加了否定感知：检查关键词前面 8 个字符内有没有「没有 / 无 / 未 / 缺乏」这类否定词。但第一版我写错了，逻辑是反的——找到否定词的时候我 `continue` 跳过继续找，结果还是返回 False。我写了一组单元测试才发现，8 个用例错了 2 个。

**第二个难点是评分门槛的尺度。** 修完否定感知后，那个项目还是能得 45.8 分，我觉得偏高。仔细看发现，测试输入里那句「请给出证据缺口和下一步建议」中的「缺口」「下一步」被当成了项目自己写了这些内容。我加了一个指令句剔除步骤 `_strip_instructions`，把祈使句先过滤掉，分数才落到合理的 23.8。

这两次修正给我的教训是：**规则系统里，边界情况比主路径重要。** 主路径我一遍就写对了，两个 bug 都出在边界上。

## 四、我如何使用 Agent，以及人工介入的地方

我主要是从**开发侧**使用 Agent 的。F1 理论学习用来快速过一遍不熟悉的概念（比如单位经济里的 CAC/LTV 口径），F3 用来在写完代码后自查文档。

Agent 对我最大的帮助不是写代码，而是**在我写测试用例时逼我把验收条件写清楚**。我原来的验收条件经常是「输出合理」这种没法测的表述，被它追问几次之后才改成「无来源数字均标为 H 或 S」。

它的局限也很明显：
- 大模型路径因为余额问题基本没跑起来，我验证的都是降级路径
- 它给出的建议有时过于笼统，比如「补充更多证据」，我还是要自己想具体补什么
- 我写的两个 bug 它都没能帮我发现——否定逻辑写反、指令句被当成证据，都是我自己写单测才抓到的

**人工纠正记录**：测试运行器第一版有 4 项失败，我一开始以为是系统问题，逐项排查后发现全是我自己的测试写错了（U4 的分发逻辑、U6 用了无效会话导致测的是 404 而不是文件类型错误）。这 4 项我没有删掉，修好之后在报告里保留了修改说明。
